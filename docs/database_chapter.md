# 2.5 Проектирование и ведение базы данных

## 2.5.1 Назначение информационного обеспечения

Задача проектирования информационного обеспечения ИС «Система ДРПЗ» заключается в определении состава данных, их структуры, связей, правил хранения и обработки, необходимых для управления процессом взыскания просроченной задолженности банка.

Информационные потоки системы включают:

| Вид потока | Содержание |
|------------|------------|
| Входящие данные | сведения о клиентах, кредитных договорах, графиках платежей, просроченной задолженности, статусах банкротства, сотрудниках ДРПЗ, нормативных ограничениях и результатах ML-моделей |
| Внутренние данные | кейсы взыскания, стадии работы, ежедневные назначения, приоритеты, история воздействий, обещания платежа, результаты распределения клиентов между операторами |
| Исходящие данные | план взыскания на текущий день, рабочие очереди операторов, отчёты KPI, сведения для руководителя, комплаенс-алерты, материалы для юридического блока |

Носителем информации является централизованная реляционная база данных. В режиме разработки используется SQLite, в production-контуре предусматривается PostgreSQL. Хранение персональных данных сопровождается аудитом действий пользователей, журналированием нарушений 230-ФЗ и разграничением доступа по ролям.

## 2.5.2 Концептуальная модель базы данных

Концептуальное проектирование выполнено на основе модели «сущность-связь». Основной объект управления в системе — клиент с одним или несколькими кредитными договорами. Вокруг него формируются состояния задолженности, платежи, воздействия, кейсы взыскания, ежедневные назначения, прогнозы и журналы контроля.

Основные сущности базы данных представлены в таблице 2.5.1.

**Таблица 2.5.1 — Сущности базы данных**

## 2.5.3 Атрибуты основных сущностей

**Client** хранит ФИО, дату рождения, пол, семейное положение, занятость, работодателя, должность, доход, количество детей, город, регион, телефоны, ежемесячные расходы, категорию клиента. Для соответствия 230-ФЗ используются атрибуты `contact_refused`, `contact_refused_date`, `refused_channels`, `is_bankrupt`, `bankruptcy_date`, `third_party_consent`, `third_party_consent_date`.

**Credit** хранит ссылку на клиента, дату открытия, плановую дату закрытия, сумму кредита, ежемесячный платёж, процентную ставку, тип продукта, статус и дату актуальности. Для аналитики используются вычисляемые признаки `delinquency_bucket` и `days_past_due`, определяемые по последнему состоянию задолженности.

**CreditState** фиксирует состояние кредита на дату: основной долг, просроченный основной долг, проценты, просроченные проценты, штрафы, дату начала просрочки, длительность просрочки и дату закрытия просрочки.

**Payment** хранит платежи по кредиту: дату, сумму, тип платежа, плановую дату, минимальный платёж, количество дней просрочки и дату актуальности записи.

**Intervention** отражает воздействие по кредиту: клиента, кредит, оператора, дату и время, тип канала, статус, длительность разговора, сумму и дату обещания, комментарий, причину отказа. Для контроля 230-ФЗ дополнительно фиксируются исходящий номер, факт представления оператора, использование утверждённого скрипта и признак контакта с третьим лицом.

**Assignment** хранит ежедневное распределение работы: оператора, клиента, ФИО должника, кредит, сумму просрочки, срок просрочки, приоритет, дату назначения, A/B-группу, метод назначения и качество матчинга. На этой сущности основаны рабочие очереди операторов и административный план взыскания на текущий день.

**CollectionCase** является центральной сущностью процесса взыскания. Она связывает клиента, один или несколько кредитов, назначенного оператора, стадию взыскания, приоритет, сумму долга, просроченную сумму, DPD, статус кейса, ML-прогнозы, дату следующего действия, счётчики контактов, психотип и рекомендованную стратегию.

**Role** описывает роли RBAC: `admin`, `manager`, `senior_operator`, `operator`, `legal_specialist`, `analyst`, `auditor`. Для роли задаются разрешения на просмотр и изменение клиентов/кредитов, совершение звонков, отправку сообщений, реструктуризацию, эскалацию, юридический модуль, отчёты, экспорт, ML и аудит.

**AuditLog** и **ViolationLog** обеспечивают контроль действий. AuditLog фиксирует входы, операции с назначениями, воздействиями, скорингом, обучением моделей и проверками. ViolationLog хранит тип нарушения 230-ФЗ, серьёзность, клиента, оператора, канал контакта, признак блокировки и подробности.

## 2.5.5 Связи между сущностями

**Таблица 2.5.3 — Описание связей**

| Связь | Тип | Описание |
|-------|-----|----------|
| Client → Credit | 1:M | один клиент может иметь несколько кредитов |
| Client → CreditState | 1:M | состояния задолженности доступны в разрезе клиента |
| Credit → CreditState | 1:M | один кредит имеет историю состояний |
| Credit → Payment | 1:M | по одному кредиту может быть много платежей |
| Client → Intervention | 1:M | с клиентом может быть выполнено несколько воздействий |
| Credit → Intervention | 1:M | воздействие привязано к конкретному кредиту |
| Operator → Intervention | 1:M | оператор выполняет множество воздействий |
| Operator → Assignment | 1:M | оператор получает рабочую очередь на день |
| Client → Assignment | 1:M | клиент может попадать в назначения в разные даты |
| Credit → Assignment | 1:M | кредит может включаться в разные ежедневные планы |
| Client → CollectionCase | 1:M | по клиенту могут быть созданы кейсы взыскания |
| CollectionCase → Credit | M:N | один кейс может объединять несколько кредитов клиента |
| Client → ScoringResult | 1:M | для клиента сохраняются результаты прогнозов |
| Credit → ScoringResult | 1:M | один кредит может оцениваться повторно |
| Client → ViolationLog | 1:M | по клиенту фиксируются нарушения комплаенса |
| Operator → ViolationLog | 1:M | нарушения могут быть связаны с оператором |
| Client → BankruptcyCheck | 1:M | клиент может проверяться по ЕФРСБ несколько раз |
| MLModelVersion → ScoringResult | 1:M | результаты прогнозов формируются конкретными версиями моделей логически через поле версии |

## 2.5.6 Логическое проектирование базы данных

Логическая модель приведена к реляционному виду. Каждая сущность реализуется отдельной таблицей Django ORM. Первичные ключи формируются автоматически как `id`. Внешние ключи задают ссылочную целостность между клиентами, кредитами, операторами, назначениями, воздействиями и журналами.

Основные отношения:

| Отношение | Первичный ключ | Основные внешние ключи |
|-----------|----------------|------------------------|
| Client | id | — |
| Credit | id | client_id |
| CreditState | id | credit_id, client_id |
| Payment | id | credit_id |
| Intervention | id | client_id, credit_id, operator_id |
| Operator | id | user_id, system_role_id |
| Assignment | id | operator_id, client_id, credit_id |
| ScoringResult | id | client_id, credit_id |
| CollectionCase | id | client_id, assigned_operator_id |
| CollectionCaseCredits | id | collectioncase_id, credit_id |
| Role | id | — |
| AuditLog | id | operator_id, client_id |
| ViolationLog | id | client_id, operator_id |

Функциональные зависимости имеют вид:

| Отношение | Функциональная зависимость |
|-----------|----------------------------|
| Client | id → ФИО, дата рождения, контакты, регион, признаки банкротства и отказа |
| Credit | id → client_id, сумма кредита, ставка, тип продукта, статус |
| CreditState | id → credit_id, дата состояния, долг, проценты, штрафы, DPD |
| Payment | id → credit_id, дата платежа, сумма, тип платежа |
| Intervention | id → client_id, credit_id, operator_id, канал, статус, результат контакта |
| Assignment | id → operator_id, client_id, credit_id, сумма просрочки, DPD, приоритет, дата |
| Operator | id → ФИО, роль, специализация, нагрузка, статус |
| CollectionCase | id → client_id, стадия, приоритет, суммы, статус, стратегия |
| ViolationLog | id → client_id, operator_id, тип нарушения, серьёзность, дата |
| AuditLog | id → действие, оператор, клиент, дата, подробности |

Модель соответствует третьей нормальной форме: повторяющиеся группы вынесены в отдельные таблицы, справочные статусы заданы ограниченными наборами значений, сведения о клиентах не дублируются в кредитах, а ежедневные назначения не смешиваются с историей воздействий.

## 2.5.7 Ведение базы данных и контроль доступа

Ведение базы данных выполняется через API, административные команды Django и пользовательский интерфейс. Операторы работают с назначенными клиентами и фиксируют воздействия. Руководители анализируют дашборды и KPI. Администратор имеет доступ к строгому плану взыскания на текущий день, построенному на таблице Assignment.

Для production-эксплуатации предусмотрены следующие меры:

| Мера | Реализация |
|------|------------|
| Разграничение доступа | роли RBAC и проверка роли `admin` для административного плана |
| Аудит действий | AuditLog для входов, назначений, воздействий, скоринга и проверок |
| Комплаенс 230-ФЗ | ViolationLog, контроль времени, частоты контактов, отказов, банкротства и третьих лиц |
| Защита персональных данных | журналирование доступа к ПДн, маскирование телефона в административном плане |
| Производительность | индексы по клиентам, кредитам, датам, статусам, операторам и приоритетам |
| Надёжность | централизованная БД, миграции Django, резервное копирование production-БД |

Таким образом, актуальная база данных ИС «Система ДРПЗ» поддерживает полный цикл взыскания: от получения сведений о клиенте и кредите до ежедневного распределения работы, фиксации контактов, ML-прогнозирования, комплаенс-контроля, аудита и подготовки управленческого плана взыскания.
